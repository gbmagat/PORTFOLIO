Undergraduate thesis · 2026

JobFinder

Ontology-based skill and geographic accessibility matching for opportunity recommendation — a job platform for Angeles City, Pampanga.

Type
Undergraduate thesis
Users
Job seekers, employers, PESO administrators
Stack
React, TypeScript, Node.js, Express, SQLite, Leaflet
Hosting
Linux VPS · nginx · systemd · Docker image

Overview

JobFinder is a research prototype for job opportunities in Angeles City. Instead of ranking openings by keywords alone, it combines ontology-based skill matching with shortest-path computation on the city's road network — so recommendations reflect both what a person can do and how far they would really travel.

What I built

  • A full-stack platform with a React and TypeScript front end, an Express REST API, and an SQLite database.
  • Separate tools for job seekers, employers, and PESO administrators.
  • Interactive maps with Leaflet and OpenStreetMap data, including a view of the underlying road graph.

Under the hood

  • Dijkstra's shortest-path algorithm implemented from scratch with a custom binary min-heap, running over an 8,282-node OpenStreetMap road graph to rank jobs by road travel distance.
  • Zod schema validation, Helmet security headers, rate limiting, and scrypt password hashing.
  • Deployed on a Linux VPS with nginx and systemd, with automated Let's Encrypt certificate renewal for HTTPS.
  • Published as a Docker image so evaluators can run the whole app with one command; container checks covered startup, authentication, uploads, and persistence.

Course final project · 2026

Our Places

A private web app for two people to discover places, plan visits, keep a shared record of what they did together, and review each visit independently.

Type
Course final project
Stack
Next.js (App Router), React, TypeScript, PostgreSQL
Maps
Leaflet with OpenStreetMap
Testing
Vitest with PGlite

Overview

Our Places covers restaurants, cafés, museums, parks, and anywhere else worth remembering. Each person's review stays hidden from the other until both have submitted — then the combined score is revealed.

Features

  • Map and search: saved places sit at their real coordinates, and pressing Enter searches OpenStreetMap for any real place to save in one step.
  • Nearest first: after you pin your location, search ranks results by distance using the Haversine formula.
  • Planned visits with email reminders, and a four-step experience log with up to six private photos.
  • A feed with filters, reactions, and private comments.

Under the hood

  • Shortest road routes: the server builds a graph from OpenStreetMap roads (respecting one-way streets) and runs Dijkstra's algorithm with a binary-heap priority queue. Roads are saved per map tile, so later routes in the same area take a fraction of a second.
  • Blind reviews are enforced in the server query itself — a partner's review is withheld until both exist.
  • Custom email and password sign-in with scrypt hashes and database-backed sessions; every request is validated with Zod and every query is parameterised.

Why Next.js instead of a separate Express server?

The app is private, so nothing may reach the browser before the server checks who is asking. Running the pages and the API in one process on one origin means the session is checked before a page renders, there is no CORS to configure, and there is a single service to deploy. The business rules still live in plain TypeScript modules with their own tests.

It's a Match

A responsive dating-app simulation developed for an academic research study on language, text styles, and perceived desirability.

Role
Full-stack developer
Type
Research platform
Stack
React, Vite, Node.js, Express, MySQL
Testing
Playwright flow checks

Overview

Participants move through scripted conversations and choose their replies, while the research team follows progress from a private dashboard. The visual designs and conversation scripts were supplied by the research team; I implemented them and built the system around them.

What I built

  • Scripted Filipino and English conversations with multiple-choice replies, in three text styles: formal, informal, and colloquial.
  • Participant-selected conversation order with resumable progress in the browser.
  • An Express API with MySQL storage for participant records and completion tracking.
  • A password-protected researcher dashboard with completion statistics and CSV export.
  • Responsive desktop and mobile layouts.

Quality checks

  • Playwright flow tests at desktop (1366×650) and mobile (390×844) viewport sizes.
  • An isolated in-memory database adapter for development checks, so tests never touch the live study.
